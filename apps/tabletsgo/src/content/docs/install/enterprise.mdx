In enterprise mode, people sign in at [Hayat](https://github.com/aidapedia/hayat) with one account across your apps. Hayat holds the
people, the workspaces (Hayat calls them tenants), the roles and the grants. Tabletsgo keeps no accounts of its own.

Moving a solo instance? See [Solo to enterprise](/docs/solo-to-enterprise). Upgrading v1.0? See [Upgrading](/docs/upgrading#v1-to-enterprise).

<H2 id="bundled">One machine: Hayat bundled</H2>

The repo's `docker-compose.hayat.yml` runs Hayat beside Tabletsgo, with its own Postgres, Redis and console. Nothing else to deploy.

```bash
echo "ENCRYPTION_KEY=$(openssl rand -hex 32)" >> .env
echo "HAYAT_MASTER_KEY=$(openssl rand -base64 32)" >> .env
alias dc='docker compose -f docker-compose.yml -f docker-compose.hayat.yml'
dc up -d
dc logs hayat | grep setup     # open the link: create Hayat's first admin
dc exec hayat hayat enrollment-code --service tabletsgo --name Tabletsgo
```

Open **http://localhost:3000** and paste the code: you become Tabletsgo's admin. Manage people and roles in Hayat's console at
**http://localhost:3001**; Hayat's mail lands in Mailpit at **http://localhost:8025** until you set `HAYAT_SMTP_URL`. Behind https, set
`HAYAT_ISSUER` and `HAYAT_CONSOLE_URL` to their public addresses and `HAYAT_DEV=false`.

Hayat runs every role in one container here. For high availability, run Hayat on its own and follow the steps below.

## What you need

- **Docker** on the Tabletsgo server.
- **Hayat 1.2.0 or newer.** No Hayat yet? Use the [bundled setup](#bundled), or [deploy one](#deploy-hayat) first.
- **Tabletsgo's address**, such as `https://db.acme.com`. People come back here after signing in.

<H2 id="set-up">Set up</H2>

<Steps>
  <Step title="Write the settings file">
    ```dotenv title="tabletsgo.env"
    TABLETSGO_MODE=enterprise
    ENCRYPTION_KEY=…                          # openssl rand -hex 32 — back it up
    PUBLIC_URL=https://db.acme.com
    HAYAT_ISSUER=https://auth.acme.com        # Hayat's sign-in, as browsers reach it
    HAYAT_API_URL=http://hayat-api:7443       # Hayat's api role, see Wiring below
    HAYAT_CONSOLE_URL=https://hayat.acme.com  # optional: the "Manage in Hayat" links
    ```

    There are no credentials to set: Tabletsgo gets them in step 3. Every setting is in [Configuration](/docs/configuration#enterprise).
  </Step>
  <Step title="Start Tabletsgo">
    ```bash
    docker run -d --name tabletsgo \
      --env-file tabletsgo.env \
      --network compose_default \
      -p 3001:3000 \
      -v tabletsgo-data:/app/data \
      --restart unless-stopped \
      ghcr.io/aidapedia/tabletsgo:latest
    ```

    `--network` joins Hayat's Docker network; leave it out if Hayat runs elsewhere. Hayat's console uses port 3000, hence `3001`.
  </Step>
  <Step title="Enroll with a code">
    In Hayat's console, open **Services → Enroll service**, pick the namespace `tabletsgo` and copy the one-time code (or run
    `hayat enrollment-code --service tabletsgo`).

    Open Tabletsgo. It shows **Connect Tabletsgo to Hayat**. Paste the code and choose who becomes **Tabletsgo admin**. Hayat registers
    Tabletsgo and hands back its credentials, which are stored encrypted. Nobody copies a secret.

    No browser? `docker exec tabletsgo node scripts/hayat-enroll.js --code hye_… [--admin-email you@acme.com]` does the same.
  </Step>
  <Step title="Sign in and add your team">
    Sign in with Hayat, then set up the team in Hayat's console: see [Your team](#team).
  </Step>
</Steps>

<H2 id="wiring">Wiring Tabletsgo to Hayat</H2>

Browsers sign in at `HAYAT_ISSUER`. The server calls `HAYAT_API_URL`, and fetches tokens from `HAYAT_AUTH_URL` (default: `HAYAT_ISSUER`).

| Setup                     | `HAYAT_API_URL`         | `HAYAT_AUTH_URL`          |
| ------------------------- | ----------------------- | ------------------------- |
| Same host, both in Docker | `http://hayat-api:7443` | `http://hayat-auth:8443`  |
| Separate servers          | `http://10.0.4.12:7443` | Leave out                 |

- **Same host:** Tabletsgo must be on Hayat's network, `compose_default` with Hayat's compose file (`docker network ls` shows it).
- **Separate servers:** keep the api role on a private network only Tabletsgo can reach.
- **One machine, for a try:** `HAYAT_ISSUER=http://localhost:8443`, `PUBLIC_URL=http://localhost:3001`, and `HAYAT_DEV=true` on Hayat.

<H2 id="team">Your team</H2>

People, rosters and grants are managed in Hayat's console. Tabletsgo shows them and links there.

1. Create a tenant for each workspace and add people to its roster. Only members see a workspace's data.
2. Grant **Workspace owner (tabletsgo)** to whoever runs it.
3. Grant **Connection user** or **Connection manager** on a connection, or on a group it is filed under.

| Role                        | Can                                                                  |
| --------------------------- | -------------------------------------------------------------------- |
| Tabletsgo admin             | The admin area: modules, mail, updates. No access to workspace data. |
| Workspace owner (tabletsgo) | The workspace: config, storage, SSH hosts and every connection.      |
| Connection manager          | Edit, export and open the connections where it is granted, and change their workflows. |
| Connection user             | Open the connections where it is granted.                            |

Changing a connection's saved workflows takes **Manage workflows** (`workflows.manage`): the connection's owner, a Connection manager
or a Workspace owner. A saved workflow runs on its schedule or webhook with the connection's credentials, so a Connection user can
open and run workflows but not change them.

A connection's **Access** tab shows who can open it and why. Enrolling with a Hayat you already run only adds the `tabletsgo`
service and its roles; your other apps, people and tenants stay as they are.

<H2 id="rotate">Rotating the secret</H2>

Make a new code on the service's **Enrollment** tab in Hayat's console and paste it at **Administration → Hayat → Re-enroll**. The old
secret stops working at once. If Hayat ever refuses the stored credentials, the setup page comes back: paste a new code.

<H2 id="deploy-hayat">Deploy Hayat</H2>

```bash
git clone https://github.com/aidapedia/hayat.git && cd hayat/deploy/compose
cp .env.example .env
# in .env: HAYAT_MASTER_KEY=$(openssl rand -base64 32), HAYAT_ISSUER and HAYAT_CONSOLE_URL
docker compose --profile console up -d
```

For production, remove `HAYAT_DEV=true` and point `HAYAT_SMTP_URL` at a real mail relay.

<H2 id="hayat-version">Hayat version</H2>

This Tabletsgo needs Hayat 1.2.0 or newer. Enrolling refuses an older Hayat, every start logs `⛔` when it is too old, and
**Administration → Hayat** shows the version that answers. A newer Hayat always works, so [upgrade Hayat first](/docs/upgrading#hayat-first).

<H2 id="when-it-fails">When it doesn't work</H2>

- **"This tabletsgo needs Hayat 1.2.0 or newer".** Upgrade Hayat. "Doesn't report its version" also means `HAYAT_API_URL` may not be
  Hayat's api role.
- **"That isn't an enrollment code".** Copy the whole code, starting with `hye_`.
- **`ECONNREFUSED` or `ENOTFOUND hayat-api`.** The server can't reach Hayat: put Tabletsgo on Hayat's network.
- **Signed in, then sent back to sign in.** `HAYAT_ISSUER` must match Hayat's exactly, scheme and port included.

<Callout kind="note" title="Hayat must be reachable">
  If Hayat is down, Tabletsgo lets nobody in until it is back: the API answers `503` with `identity_unavailable`. People already
  signed in stay signed in and see **Can't reach the identity service (Hayat)**. The console retries on its own and carries on, with
  their tabs, once Hayat answers.
</Callout>
