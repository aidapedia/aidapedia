The compose file's defaults are for a machine you sit at. Before anyone else signs in, go through this list.

## The issuer is https

`HAYAT_ISSUER` is the public address of the `auth` role, and the OpenID issuer every token names. Outside development it must start
with `https://`, or Hayat refuses to start. The session cookie is `Secure` whenever the issuer is https.

Terminate TLS in front of `auth` with any reverse proxy and pass requests to port `8443`. Use the issuer's exact address: tokens are
checked against it, and changing it later invalidates every token and session cookie already handed out.

```nginx title="nginx (excerpt)"
server {
  listen 443 ssl;
  server_name auth.example.com;
  location / {
    proxy_pass http://hayat-auth:8443;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto https;
  }
}
```

## Development mode is off

`HAYAT_DEV=true` allows an http issuer, http redirect URIs anywhere, and cookies without `Secure`. It is in `.env.example` so the quick
start works on localhost. Set it to `false` (or remove it) on anything other people reach. Without it, a sign-in client's redirect URIs
must be https, except for `localhost`.

## The master key is kept safe

`HAYAT_MASTER_KEY` encrypts the signing keys in the database. Store it in your secret manager, not in the repo, and back it up
separately from the database: a database backup without the key can't sign tokens, and the key without the database is useless.
Losing it means re-issuing every signing key, which signs everyone out of every app.

## Each role is reachable only by who needs it

| Role | Who reaches it |
| --- | --- |
| `auth` (8443) | The internet, through your TLS proxy |
| `admin` (8080) | The console only |
| `api` (7443) | Your services only, on a private network |
| health (9090) | Your orchestrator's probes |

The console can sit behind your VPN or SSO proxy as well: it only needs to reach `admin`, and people's browsers need to reach it and
`auth`.

## Mail goes through a real relay

Account emails (choose your password, reset it) are how people get in. Set `HAYAT_SMTP_URL` to your provider and `HAYAT_MAIL_FROM` to an
address it may send from. Without `HAYAT_SMTP_URL`, Hayat writes each email to its log instead of sending it. See [Email](/docs/email).

## Rate limits are shared

With more than one `auth` pod, set `HAYAT_REDIS_URL`. Without it each pod keeps its own sign-in counters in memory, so the limits are
per pod rather than per instance.

## The database is backed up

Everything Hayat knows is in its PostgreSQL database: accounts, tenants, the tree, grants, contracts, clients and the encrypted signing
keys. Back it up like any production database, together with a separately stored copy of the master key. Run PostgreSQL with a
replicated setup such as CloudNativePG or Patroni if Hayat must survive losing a machine.

## Images have a home

People's pictures and logos live outside the database, on a volume the `auth` and `admin` roles both mount or in an S3-compatible
bucket. With several pods, use a bucket or a ReadWriteMany volume, and back it up with the database. See [Image storage](/docs/storage).

## The issuer's host is final

Passkeys belong to the issuer's host name, so moving Hayat to another host means everyone adds their passkeys again, and an IP address
can't hold them. Pick the host name you will keep.

## Account security suits you

New passwords are checked against Have I Been Pwned by default. Consider `HAYAT_SESSION_IDLE_TIMEOUT` to end sessions left unused, and
Cloudflare Turnstile (`HAYAT_TURNSTILE_*`) if bots find your sign-up page. Set up [sign-in methods](/docs/sign-in-methods) and, for
tenants that need it, [two-step verification](/docs/two-step-verification).

## Migrations run before each release

Run `hayat migrate` once per release before starting the new roles. The compose file does this with its `hayat-migrate` service; in
Kubernetes, use a Job or an init step. See [Upgrading](/docs/upgrading).

## Lifetimes suit you

The defaults are a 14-day session, 10-minute access tokens, 30-day refresh tokens and a 90-day key rotation. Shorter sessions mean
signing in more often; see [Configuration](/docs/configuration#lifetimes).
